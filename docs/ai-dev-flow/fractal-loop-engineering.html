ループを入れ子にするのは、効く所だけ

AIエージェントに「一回ずつ指示する」段階から、「自分で回るループを設計する」段階へ進んだ開発組織が次に迷うのが、ループを何重に重ねるかです。このページでは、ループエンジニアリングとフラクタルエンジニアリングの関係を整理し、Codexを使う開発組織が、要件定義からリリースまでの流れに入れ子のループを必要な範囲だけ組み込むための判断基準と導入手順をまとめます。

ループエンジニアリングと、フラクタルエンジニアリング

ループエンジニアリングは、エージェントに毎回プロンプトを打つ代わりに、エージェントが「行動する → 結果を観察する → 次を決める」を目標達成まで繰り返す仕組みを設計する考え方です。2026年6月ごろから広く使われるようになった呼び方で、プロンプト、コンテキスト、ハーネスの設計に続く層として整理されています。

フラクタルエンジニアリングは、まだ定義が定まった用語ではありません。このページでは「ループの中に子のループを置き、どの層のループも同じ型（同じ契約）で設計すること」と定義して使います。フラクタル図形がどこを拡大しても同じ形に見えるのと同じで、親のループも子のループも「作る → 確かめる → 直す → 止まる」という同じ形をしています。

全体像：フェーズを回す親、作業を仕上げる子

要件定義からリリースまでの5つのフェーズを、親セッション（外側のループ）が順に進めます。各フェーズの中で、切り出せる作業だけをサブエージェント（内側のループ）に任せます。層は2つに留めます。

図は左から右へ読みます。フェーズの中の小さな円の数が、そのフェーズで入れ子を使う度合いを表しています。開発フェーズは独立したタスクを並列に任せるので円が多く、要件定義とリリースは子に調査や下書きだけを任せるので1つです。

この図に描いていないこともあります。差し戻しはテストから開発への経路だけを代表として描いていますが、設計の誤りが見つかれば設計へ、要件の誤りなら要件定義へ戻ります。また、フェーズの境界は実際には重なることがあり、小さな修正ではフェーズを省略して構いません。

どの層のループも、同じ6項目の契約で設計する

フラクタルな構造の利点は、層が変わっても設計の考え方が変わらないことです。親のループにも子のループにも、次の6項目を必ず決めます。どれか1つでも曖昧なループは、入れ子にする前に1層のまま直します。

外側と内側のループの契約。項目は同じで、中身の粒度だけが違う。
項目外側（親セッション）内側（サブエージェント）
目的フェーズの成果物を完成させて次へ渡す切り出された1つの作業を仕上げる
入力前のフェーズのファイル（要件書、設計書など）親が書いた指示文と、読むべきファイルのパス
作る成果物を書く、作業を分けて配るコード、テスト、調査メモを書く
検証フェーズの完了条件（要件との対応、網羅率など）テスト、型チェック、lint などの機械的な判定
停止条件差し戻し回数の上限、人の承認試行回数の上限、同じ失敗の繰り返しの検知
出力次のフェーズ用のファイルと進捗の記録親への要約（何をして、何が残ったか）
受け渡しは会話ではなくファイルで行う

サブエージェントは、親との会話の流れをそのまま覚えているわけではありません。要件、設計、タスク一覧、進捗をリポジトリ内のファイルに置き、子にはそのパスを渡します。ファイルに残っていれば、途中で止まっても別の人や別のセッションが続きから再開できます。

# 例：フローの作業ファイルをリポジトリに置く
docs/flow/<issue番号>/
├── requirements.md   # 受け入れ条件（人が承認した印を残す）
├── design.md         # 設計と、要件との対応表
├── tasks.md          # タスク一覧、依存関係、担当ファイル
├── progress.md       # 各タスクの状態、試行回数、失敗の記録
└── test-matrix.md    # 受け入れ条件とテストの対応表

Codexの機能との対応

Codexには、入れ子のループを組むための部品がひと通りそろっています。組織として押さえておきたいのは、サブエージェントの入れ子の深さは既定で1段（親の直下の子まで）という点です。このページの2層構成は、この既定値のまま組めます。

契約の項目とCodexの機能の対応（2026年9月時点の公式ドキュメントに基づく）
役割Codexの機能このフローでの使い方
共通ルールAGENTS.mdフェーズの定義、作業ファイルの置き場所、完了条件の書き方を記述する。親も子も同じ規約を読む。
子の役割定義カスタムエージェント（.codex/agents/ の TOML。name、description、developer_instructions が必須）「調査役」「実装役」「レビュー役」などをプロジェクトに置き、リポジトリで管理する。sandbox_mode で調査役を読み取り専用にできる。
入れ子の深さagents.max_depth（既定 1）既定のまま使う。子がさらに子を作らないので、コストと追跡が読みやすい。
並列数agents.max_threads（既定 6）開発フェーズの並列度の上限。タスク分割の粒度と合わせて決める。
子の起動明示的な指示でのみ起動親への指示に「このタスクごとに1つずつ子を起動し、全員の完了を待って要約する」と書く。
親の継続/goal（pause／resume／clear）開発フェーズの親に「tasks.md の全タスクが完了し、テストが通るまで」のような検証できる終了条件を渡す。
検証役/review未コミットの変更、コミット、ベースブランチとの差分をレビューさせ、修正はさせずに指摘だけ受け取る。
CIへの組み込みcodex exec（既定は読み取り専用、--json、--output-schema）PRごとの検査や要約をCIから非対話で実行し、結果を構造化して次の処理に渡す。
定期実行Automations（Codexアプリのスケジュール実行）依存更新や失敗テストの調査など、決まった間隔で回す外側のループ。Gitリポジトリでは worktree で実行され、手元の変更と分かれる。
作業の分離Git worktree並列で動く子が同じ作業ツリーを書き換えないように分ける。
設定名と既定値は変わる可能性があります

Codexは更新が速く、ドキュメントの移転も続いています。導入時は出典の公式ドキュメントで最新の設定名と既定値を確認してください。

フェーズ別：どこまで子に任せるか

入れ子を使う度合いはフェーズごとに違います。ラベルの意味は、積極的に使う、限定して使う、人が決めるです。

1

要件定義

限定して使う人が承認
親がやること
関係者との対話で要件を固め、受け入れ条件を書く。判断そのものは親と人で行う。
子に任せること
既存コードの関連箇所、過去のIssue、似た機能の調査。読み取り専用の調査役で十分。
完了条件
受け入れ条件が「Given／When／Then」のように検証できる形になっている。「いい感じに」「なるべく」などの曖昧な言葉が残っていない。
入れ子を広げない理由
要件は利害関係者の意図で決まり、機械で合否を判定できない。ここを子に分けると、もっともらしいが誰も合意していない要件が増える。
2

設計

限定して使う人が承認
親がやること
設計書を書き、実装を独立したタスクに分けてタスク一覧にする。分け方の基準は「触るファイルが重ならないこと」。
子に任せること
複数の設計案の並行検討、影響範囲の調査。子ごとに別の案を担当させ、親が比べる。
完了条件
すべての受け入れ条件が設計のどこかに対応している。タスクの依存関係が循環していない。
ポイント
タスクの分け方が、そのまま次の開発フェーズの並列度になる。依存のあるタスクを無理に並列にしない。
3

開発

積極的に使う
親がやること
タスク一覧から依存のないものを選んで子に配り、戻ってきた要約で進捗ファイルを更新する。/goal で「全タスク完了かつテスト通過」まで続けさせる。
子に任せること
1タスクずつ、専用の worktree で「実装 → 単体テスト → 直す」を回す。入れ子の効果が最も出るのはここ。
完了条件
テスト、型チェック、lint が通る。子の「できました」という自己申告は完了条件にしない。
入れ子を使わない場合
変更が数ファイルで済む、またはタスク同士が同じファイルを触る場合は、親1つで進める方が速い。
4

テスト

積極的に使う
親がやること
統合テストとE2Eを回し、受け入れ条件ごとに「どのテストで確かめたか」の対応表を作る。
子に任せること
受け入れ条件ごとのテスト作成と、/review によるレビュー。レビュー役は実装役とは別の子にする。
完了条件
すべての受け入れ条件にテストが対応し、全件通過。重大なレビュー指摘が残っていない。
ポイント
作る役と確かめる役を分けることが、入れ子の一番大事な使い道。同じ子に自分の成果を評価させない。
5

リリース

限定して使う人がマージ・デプロイ
親がやること
PRを作り、説明文に要件、設計、テスト結果へのリンクをまとめる。
子に任せること
リリースノートと変更履歴の下書き、ロールバック手順の確認。
完了条件
CIが通っている。PRの説明から要件までたどれる。戻し方が書かれている。
人が決める理由
マージとデプロイは取り消しにくい操作。ループはここで止まり、判断材料をそろえて人に渡す。

入れ子を使うか、使わないかの判断

入れ子にすると、並列化とコンテキストの分離という利点が得られる代わりに、コスト、待ち時間、要約での情報の欠落が増えます。フェーズ単位ではなく、作業ごとに次の条件で判断します。

入れ子（サブエージェント）を使う条件と、使わない方がよい条件
観点使う使わない
分けやすさ作業が独立した単位に分かれ、触るファイルが重ならない分けた作業が同じファイルや同じ判断に依存している
検証テストや型チェックなど、機械的に合否を判定できる合否が人の好みや合意でしか決まらない
コンテキスト調査結果やログが大きく、親の会話に入れると埋もれる必要な情報が少なく、親がそのまま扱える
規模親1つでは時間がかかりすぎる量がある数ファイルの修正など、分ける手間の方が大きい
取り消しやすさ失敗しても worktree やブランチを捨てれば戻せる本番操作、外部への送信など、取り消しにくい
視点作る役と確かめる役を分けたい（レビュー、テスト）1つの視点で十分な作業
迷ったら1層から

「使う」の列に当てはまるのが1つか2つなら、まず親1つのループで回し、検証と停止条件が安定してから子に分けます。1層でうまく回らないループは、入れ子にしても直りません。

組織への導入手順

個人の工夫として始まった入れ子のループを、組織の開発フローにするための段階です。各段階には「次へ進む条件」を置き、満たさないうちは広げません。

  1. 1層のループを共通化する

    フェーズの定義、作業ファイルの置き場所、完了条件の書き方を AGENTS.md にまとめ、全員が同じ規約で1層のループを回す。

    次へ進む条件：完了条件が機械的に判定できる形で書かれ、差し戻しの理由が記録されている。

  2. 子の役割をリポジトリで管理する

    調査役、実装役、レビュー役などのカスタムエージェントを .codex/agents/ に置き、コードと同じようにレビューを通して変更する。個人の設定に散らばらせない。

    次へ進む条件：役割ごとの権限（読み取り専用か、書き込み可か）が決まり、変更の担当者が決まっている。

  3. 開発とテストのフェーズだけ入れ子にする

    効果が出やすく、失敗しても戻しやすい2つのフェーズから始める。要件定義と設計は、子を調査と案の比較だけに使う。

    次へ進む条件：下の表の指標が、1層のときより悪化していない。

  4. 定期実行とCIに広げる

    依存更新や失敗テストの調査を Automations で、PRごとの検査を codex exec で回す。いずれも結果は人が確認できる場所に集める。

    次へ進む条件：誰も見ていない定期実行がない。止め方と担当者が決まっている。

導入の効果を見るための指標の例。数値の目標は組織ごとに決める。
指標見ること悪化したときの疑い
差し戻し率フェーズの完了後に前のフェーズへ戻った割合完了条件が曖昧、または作業の分け方が悪い
人のレビュー時間PR 1件あたりに人がかけた時間子の成果の要約が足りない、PRが大きすぎる
試行回数子が1タスクを終えるまでの試行の回数タスクが大きすぎる、テストが不安定
使用量PR 1件あたりの使用量入れ子にしなくてよい作業まで分けている
リリース後の不具合リリース後に見つかった不具合の件数確かめる役が作る役と分かれていない

停止条件とコスト

入れ子にすると、コストと失敗は層の数に応じて掛け算で増えます。止まる仕組みは層ごとに用意し、下の層で止まったら上の層に判断を返します。回数は出発点の目安で、組織で調整します。

層ごとの停止条件の例
層止める条件止まったとき
内側（子）同じテストが3回続けて失敗した。実行時間が上限を超えた。試したことと失敗内容を進捗ファイルに書き、親へ報告して終わる。
外側（親）同じフェーズへの差し戻しが2回を超えた。自動で回すのをやめ、人に判断を求める。要件か設計に問題がある合図と考える。
全体1件あたりの使用量の目安を超えた。取り消しにくい操作の直前。人の承認を待つ。

よくある迷い

入れ子を3層以上にしてもよい？
Codexでは agents.max_depth を上げれば可能ですが、まず2層で検証と停止条件が安定していることが前提です。層を増やすと、要約を重ねるたびに情報が落ち、どの子が何をしたかを追うのも難しくなります。3層目が必要になるのは、大規模な移行のように、子の作業自体がさらに独立した単位に分かれる場合に限られます。
子の数は多いほど速い？
速くなるのは独立したタスクがある分までです。依存のあるタスクを同時に始めると、前提がそろう前に後続が進んで手戻りになります。並列にできるのは、設計フェーズで「触るファイルが重ならない」と確認できたタスクだけです。
子の要約だけで親は判断できる？
成功時は要約で足ります。失敗時は要約で詳細が落ちやすいので、子には失敗ログと試したことを進捗ファイルに残させ、親と人がそこを読めるようにします。
要件定義を全部AIに任せられない？
調査や整理は任せられますが、何を作るかの合意は人の仕事です。合否を機械で判定できない作業を入れ子にすると、もっともらしいが誰も承認していない判断が積み重なります。
フラクタルエンジニアリングは導入すべき流行語？
名前より中身で判断してください。このページの内容は「入れ子のループを同じ契約で設計し、効く所だけ使う」という設計の話です。自組織のフローで独立して分けられ、機械的に確かめられる作業がどこにあるかを先に探すことが出発点です。
