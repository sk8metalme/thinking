# thinkingのGitHub Pages公開Skill

このSkillは、`thinking`リポジトリの`docs/`配下にある単一HTML記事を作成・レビューし、GitHub Pagesへ安全に公開できる状態へ整えるときに使います。

対象は次の範囲です。

- 新規記事の構成、本文、図表、一覧登録の準備
- 既存記事を変更する前の読者・目的・方向性の確認
- 相対リンク、アクセシビリティ、レスポンシブ表示、公開構成の確認
- GitHub Actionsによる公開前の検証と、Pages設定の読み取り

このSkillは、ユーザーの明示的な確認なしにcommit、push、GitHub Pages設定変更、公開後の外部操作を行いません。

## 1. まずリポジトリの事実を読む

変更前に、次を読みます。

1. `AGENTS.md`
2. `README.md`
3. `docs/index.html`
4. 作成対象と同じカテゴリにある既存記事
5. `git status --short --branch`

既存記事からサイトの文章量、色、フォント、余白、フッター、インタラクションの作法を確認します。既存のユーザー変更や別タスクの差分は保持し、対象ファイルを広げません。

## 2. 記事作成・改稿前にユーザーと意図を確定する

記事の新規作成や本文・構成・図表の改稿を始める前に、ユーザーへ次を確認します。リポジトリで確認できる事実を質問してはいけません。先に調査し、意図や判断だけを聞きます。

- 想定読者：誰が、どの程度の前提知識で読むか
- 目的：読後に何を理解し、判断し、実行してほしいか
- 方向性：解説、設計案、比較、手順、意思決定記録などのどれか
- 範囲：含めるもの、含めないもの、必要な深さ
- 不明点：用語、前提、事実、優先順位、出典、未確定の主張
- 表現：文章、表、図、インタラクションのどれを中心にするか

回答を次の短いブリーフにまとめ、ユーザーの意図と一致していることを確認してからファイルを変更します。

```text
想定読者：
ページの目的：
読後に期待する行動：
扱う範囲と深さ：
確認が必要な不明点：
本文・表・図の役割分担：
```

重要な不明点や方向性の候補が残る場合、推測で進めません。具体的な選択肢と推奨案を示してユーザーに確認し、確認が得られるまで記事を作成・改稿しません。ユーザーがすべてを指定済みなら、ブリーフを提示して暗黙の前提がないことだけ確認します。

公開構成だけを検証し、記事本文を変更しない場合はこの確認を省略できます。ただし、検証中に本文や方向性の変更が必要になった時点で、作業を止めて確認します。

## 3. 記事を作る

- `docs/<category>/<slug>.html` に単一HTMLを作成します。
- slugとカテゴリ名は小文字の英数字とハイフンにします。
- `<!DOCTYPE html>`、`<html lang="ja">`、viewport、title、descriptionを置きます。
- CSSとJavaScriptはHTML内に置き、外部依存は必要性と失敗時の表示を確認します。
- 見出し階層、表の見出し、リンクの目的、ボタンやタブの状態を意味的に表します。
- JavaScriptが無効でも、記事の主張・前提・結論が読めるようにします。
- 記事フッターから、配置階層に合った相対パスで`thinking`トップへ戻れるようにします。
- `docs/index.html`へタイトル、日付、概要、タグを含むリンクを登録します。
- 既存記事と同じ内容を重複させず、読者が必要とする前提・用語・判断基準は省略しません。
- 長さを減らすときは、必要な説明ではなく重複・曖昧な修飾・結論に寄与しない例を削ります。

## 4. 図・表・文章を選ぶ

次の順で選びます。

1. 一文または段落で十分なら文章にする
2. 項目・数値・役割・条件を横に比較するなら表にする
3. 関係、工程、状態遷移、責務分担、因果関係を同時に追う必要があるなら図を検討する

図を選んだ場合は`diagram-design` Skillを使います。

- まず意味パターン、次に視覚タイプを選び、該当するリファレンスを読みます。
- 対象読者、`doc-inline`などのサイズ、詳細度、図の目的を先に決めます。
- 図を描く前に、その型と図で伝える範囲を短くユーザーへ共有します。
- 既存サイトの配色・日本語フォント・余白に合わせ、デフォルトのスキンを無断で混在させません。
- 図には本文の説明、`role="img"`、空でない`title`と`desc`、日本語フォントフォールバックを用意します。
- 色、位置、線種だけに重要な意味を持たせず、テキストでも判別できるようにします。
- 単純な一覧を図にせず、ノード・線・装飾を削っても意味が保てる構成にします。
- 図を使わない方が明快な場合は、理由を説明して表または文章にします。

図だけを置いて説明を省略してはいけません。図が表している範囲、読者が見る順番、表していない例外や限界を本文で説明します。

## 5. ローカル検証

最低限、次を実行します。

```sh
test -f docs/index.html
test -f docs/.nojekyll
git diff --check
python3 -m http.server -d docs 8000
```

サーバー起動中に、トップページと変更した記事をブラウザで開き、次を確認します。

- デスクトップ幅とモバイル幅で横スクロールや文字の欠落がない
- 見出し、表、図、コード、操作部品の順序と意味が追える
- キーボードフォーカスが見え、操作部品の状態が読める
- ダークモードと`prefers-reduced-motion`で情報が失われない
- すべてのローカル`href`、`src`、ページ内アンカーが存在する
- 新しい記事が`docs/index.html`から到達できる
- 記事のフッターからトップへ戻れる
- 秘密情報、`localhost`、未解決のTODO、作業用ファイルが公開対象にない

`.github/workflows/pages.yml`にも同じ公開構成の検査があります。検査コマンドをworkflowに合わせて実行し、PRで失敗する条件を先に解消します。

## 6. Pages公開の準備

Pages設定は読み取りだけ行います。

```sh
gh api repos/sk8metalme/thinking/pages \
  --jq '{url: .html_url, status: .status, source: .source, build_type: .build_type}'
```

現在のsourceが`main`の`/docs`を使うlegacy方式なら、ユーザーへ「PagesのSourceをGitHub Actionsへ切り替える必要がある」と伝えます。Settingsの変更をAPIやUIから自動実行しません。READMEには設定手順を追加せず、このSkillの公開準備で案内します。

変更を公開できる状態にしたら、次を報告します。

- 変更したファイル
- ユーザー確認済みの読者・目的・方向性
- 実行した検証と結果
- Pages設定で必要な手動作業
- commit・pushを行っていない場合は、その旨
- 次にできるタスク候補
