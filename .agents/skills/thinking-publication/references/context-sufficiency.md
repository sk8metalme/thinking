# コンテキスト充足・分量監査

## 目的

長編の分量を、文章の水増しではなく読者に必要な情報の充足で作る。特に `book-300-plus-exhaustive` では、ページ数を先に埋めてから内容を合わせるのではなく、読者の課題・判断・実行・検証に必要なコンテキストを先に洗い出す。

## 1. コンテキスト契約

本文を書く前に、次の項目を `known`、`researchable`、`user-needed`、`assumption`、`out-of-scope` のいずれかで記録する。

| 項目 | 確認すること |
| --- | --- |
| 読者 | 知識、経験、年齢・役割、読める言語、想定する利用場面 |
| 読後の成果 | 理解、判断、操作、成果物、到達条件 |
| 問い・範囲 | 本で答える問い、答えない問い、対象期間、対象地域・制度 |
| 制約 | 時間、予算、環境、利用可能な道具、アクセシビリティ |
| 実行条件 | 読者が実際に行う手順、前提、入力、期待結果、失敗時の分岐 |
| 判断条件 | 選択肢、評価軸、トレードオフ、結論が変わる条件 |
| 証拠 | 一次情報、公式情報、データ、反証、更新頻度、参照範囲 |
| 出力仕様 | PDF／HTML、用紙、文字サイズ、段組み、図表、索引、リンク要件 |
| 更新性 | 発表待ち、変更される規則、再確認日、更新担当・方法 |

`user-needed` は推測で埋めない。`assumption` を置く場合は、本文と出版計画の両方に明示し、結論やページ配分を大きく変える仮定ならユーザー確認へ戻す。

## 2. 不足台帳

目次の各章について、次の表を埋める。

| ID | 不足しているもの | 読者課題への影響 | 解決方法 | 状態 |
| --- | --- | --- | --- | --- |
| C-001 | 例：対象カテゴリの登録条件 | 読者が参加可否を判断できない | 公式告知を確認 | open / resolved |

不足は少なくとも次の種類に分類する。

- `reader`：読者の経験、制約、目的、利用環境が不明
- `domain`：用語、仕組み、前提知識、制度の構造が不明
- `operation`：手順、入力、期待結果、失敗時の分岐が不明
- `decision`：選択肢、比較軸、反対意見、適用条件が不明
- `evidence`：一次情報、データ、反証、参照箇所が不足
- `example`：具体例、反例、ケース、練習、検証課題が不足
- `boundary`：限界、例外、更新、リスク、範囲外が不明
- `format`：用紙、文字サイズ、図表密度、相互参照、アクセシビリティが不明

## 3. 不足の解決ルール

不足ごとに、次の順で扱う。

1. `evidence`、`domain`、`operation`、`boundary` は、一次情報・公式文書・元データを追加調査できるか確認する。
2. `reader`、`decision`、`format` のうちユーザー固有で結果が変わるものは、最大5問程度にまとめて確認する。質問には、未回答時の安全な既定値と影響範囲を添える。
3. `example` は、実在の事例か、仮想例か、読者が再現できる練習かを分ける。架空の事実や勝率を作らない。
4. 外部確認でも埋まらないものは `out-of-scope` または `未発表` として本文から断定を外し、必要なら付録の未解決事項に残す。
5. 解決不能な不足をページ数達成のために言い換え・反復・装飾で埋めない。実測ページ数が短くなるなら、範囲拡張の案を示して再確認する。

## 4. 有意義な分量の増やし方

ページを増やす理由は、少なくとも一つの読者課題または不足台帳項目に対応している必要がある。採用候補は次のとおり。

- 一次情報の背景、定義、適用条件、更新履歴
- 仕組みの分解、因果関係、前提と反証
- 手順の準備、期待結果、失敗分岐、復旧、完了条件
- 条件の異なる比較例、反例、ケーススタディ、再現可能な練習
- 判断表、チェックリスト、ワークシート、記録テンプレート
- 限界、例外、リスク、倫理・安全上の注意、更新手順
- 用語集、参考文献、索引、出典対応表など、本文を探し直すための付録

次は分量として認めない。

- 同じ結論や定義の言い換え
- 見出しを大きくする、余白や改ページを増やす、行間を不自然に広げる
- 新しい条件・判断・検証を含まない似た例の反復
- 出典や前提のない断定、架空の数字、検索できない引用
- 本文に必要な説明を付録へ移しただけの見かけ上の増量

## 5. 長編の停止条件と再見積もり

`book-300-plus-exhaustive` では、次の順で進める。

1. コンテキスト契約、不足台帳、目次案、ページ配分を作る。
2. ユーザー固有の `user-needed` と、結果を大きく変える `assumption` を確認する。
3. 5〜10ページ程度の試作をレンダリングし、組版と情報密度を測る。
4. 各章で「読者の到達点、証拠、具体例または練習、反例・限界、検証方法」を確認する。
5. 1〜2章ごとに実測ページ数を再見積もり、計画との差分と原因を記録する。
6. 目標に届かない場合は、不足台帳に戻る。重要な不足が `open` のままなら停止してユーザーへ確認する。

## 6. ユーザー確認のテンプレート

質問は、答えによって目次・主張・ページ配分・組版が変わるものに限定する。

```text
本の対象カテゴリ／読者環境はどれですか？（未指定時の既定値：○○）
読者が週に使える時間・期間はどれくらいですか？（既定値：○○）
本で扱う範囲から外したいものはありますか？（既定値：○○）
PDFの用紙・文字サイズ・図表密度に希望はありますか？（既定値：B5、本文10.5〜11pt）
実体験・手持ちの資料・公開してよいデータはありますか？（なければ公式情報中心）
```

回答後、コンテキスト契約と不足台帳を更新し、変更された章とページ配分を再提示してから本文を進める。
